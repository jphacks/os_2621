## 👥 5体エージェント体制と役割分担
従来の「Aさん・Bさん・Cさん」の役割分担は終了しました。あなたがフロント・バックエンド・インフラ・AI・UI/UX・テストのすべてを担当します。
`prompts/loop_engineering_specification.md` に基づき、以下の5体協調で開発を進めてください。

1. **Orchestrator（司令塔・進行管理）**:
   - 各タスクの完了を検知し、人間の判断を仰がずに次フェーズへ自動遷移する。
   - ループ回数は**最低5回**以上回し、全てのバグが解決するまで絶対にループを終了しない。
2. **loop-planner (`pro` / Read-only)**:
   - JPHACKS審査基準および悩みを抱える当事者心理を反映した、緻密な仕様・受け入れ基準（Acceptance Criteria）を策定。
3. **loop-developer (`pro` / Write & Edit)**:
   - フロントからバックエンド、WebRTC/音声通話、AIプロンプト、型定義まで全レイヤーを自律実装・修復。
4. **loop-tester (`flash` or `pro` / Write & Run)**:
   - E2E/単体テストの実行、ビルド検証（`npm run build`）、型チェック（`tsc --noEmit`）、エラーログの要約フィードバック。
5. **loop-reviewer (`pro` / Read-only)**:
   - 単なる構文チェックにとどまらず、以下の**多面的な視点**で厳格に審査を行う。
     - **【JPHACKS審査員目線】**: 「課題解決になっているか」「実機デモで感動を生むか」「スケーラビリティがあるか」
     - **【当事者ユーザー目線】**: 「精神的負荷がないか」「突き放された・見放されたと感じないか」「安心感があるか」
     - **【セキュリティ監査】**: APIキー・シークレットが差分やコミットに含まれていないかを最優先で検査。

## 📋 実行タスク一覧（自動順次実行フロー）

以下のフェーズを順番に実行し、各フェーズの完了条件を満たしたら自動で次のフェーズへ進んでください。

### 【Phase 1: Git最新ブランチのマージ & 基盤統合】
- 最新の `origin/vercel` と `origin/claude/gemini-fallback` をマージする。
- 発生したコンフリクトをすべて解決し、既存の型エラー・依存関係エラーを解消する。
- `npm run build` が通る状態をベースラインとして確立する。

### 【Phase 2: 年代別（中・高・大/院）マッチング制御の実装】
- ユーザー属性に年代（中学生、高校生、大学生/大学院生、社会人等）を確実に保持・分類する仕組みを構築。
- マッチングアルゴリズム（`lib/matching/`）を拡張し、同年代または適切な年代間でのみマッチングが成立するようフィルタリング＆スコアリングを制御する。
- 境界値テスト（年代未設定、境界年代など）を作成し、マッチング制御が確実に機能することを検証する。

### 【Phase 3: ページ遷移フローの完全制御（不正遷移防止ガード）】
- 現状の「順番を無視して自由にURL遷移できてしまう問題」を解決する。
- 傾聴チャット → 要約確認・同意 → マッチ候補提示 → 双方同意 → ファシリテーションチャット という正規の体験フローを強制するステートマシン/ミドルウェア/ルートガードを実装する。
- 未完了ステップや不正アクセス時には、適切な前段階へリダイレクトし、トーストや温かみのある案内を表示する。

### 【Phase 4: UI/UXの最適化 & スクリーンショット検証】
- UIを要件にマッチするよう最適化する（Tailwind CSS, レスポンシブ対応、アクセシビリティ、余白、アニメーション）。
- フロントエンド修正時は適宜スクリーンショット等で画面の崩れ・破綻がないか検証する。
- 悩みを抱えるユーザーが落ち着ける、優しく洗練されたトーン＆マナー（配色・フォント・UIコンポーネント）に整える。

### 【Phase 5: 各種AIプロンプトの反復改善 & 評価】
- プロンプト（傾聴、要約、タグ付け、マッチング評価、ファシリテーター）を徹底的に改善する。
- 「実際に悩みを抱えるユーザー目線」で、形式的な回答ではなく、心に寄り添う自然な対話になっているかを評価・反復修正する。
- 要約が本人の意図を歪めず、タグ付けが的確に行われるか、複数パターンのダミー相談文で検証する。

### 【Phase 6: 双方承認による通話機能（音声通話/WebRTC）の実装】
- テキストチャットルームにおいて、双方が「通話に同意」した場合にのみ起動する通話UI/シグナリング機能を実装する。
- どちらか一方の同意だけでは開始できず、心理的安全性を担保するUI設計（いつでもワンタップで切断、マイクミュート、通話前確認モーダル）にする。
- 音声通話中もAIファシリテーターがテキストチャット上で見守る安心感を演出する。

### 【Phase 7: 心に寄り添う相談窓口（ホットライン）への対話的誘導】
- 危機判定（自傷・他害・深刻な危機）時に、**「機械的に突然窓口一覧を表示してチャットを打ち切る」仕様を完全に廃止**する。
  - （※突然一覧を突きつけられると、ユーザーは見放された・拒絶されたと感じる重大なリスクがあるため）
- ユーザーの辛い気持ちを最大限に受容・尊重しながら、「専門の方と一緒に考えることもできるよ」「今とても頑張ってきたんだね」と優しく対話を続け、ユーザー自身のペースで相談窓口を頼れるよう導く対話プロンプトおよびUI遷移ロジックを実装する。

### 【Phase 8: 全機能バグ修正・コード最適化・リグレッション検証】
- 新機能追加に伴い、既存機能（マッチング、認証、チャット、要約、安全性）に不具合が生じていないか全テストを実行。
- TypeScriptの型エラー（`tsc --noEmit`）、ESLintエラー、ビルドエラー（`npm run build`）を完全にゼロにする。
- 最低5回以上のループ検証を経て、エッジケース（ネットワーク切断、リロード、空データ）でもクラッシュしないことを確認する。

### 【Phase 9: Vercel公開確認 & GitHubプッシュ】
- Vercel環境変数（`.env.example` の整備）およびビルド出力を最終確認する。
- **【最重要】APIキー・シークレットがコミット差分に含まれていないことを厳格にスキャンする。**
- すべての確認が完了したら、作業成果を適切なコミットメッセージ（`feat:`, `fix:` 等）でコミットし、GitHubリモートリポジトリへプッシュする。
- 完了後、JPHACKS審査員に向けたアピールポイント（審査基準1〜4への対応状況）と実装完了サマリーを報告する。
